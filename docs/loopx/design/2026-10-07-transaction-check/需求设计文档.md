# Ethereum 交易核验设计文档

## 二、需求信息

### 2.1 需求背景

用户授权创建分支完成面向链上新手的只读交易核验 MVP。任务是将交易线索加工为可核查的事实与解释，不承诺市场判断。来源为 `.loopx/intake/2026-10-07-transaction-check/requirements.md`；`clarification.md` 记录授权与现有边界。方案见同目录 `设计提案.md`。

### 2.2 需求范围

Ethereum 主网，原生 ETH 外层交易与现有 Uniswap V3 WETH/USDC 0.05% 池事件。排除内部 trace、后续资金路径、身份判定、其他协议、CEX、签名、LLM、存储和后台任务。Support lenses: api-designer, architecture-designer。

## 三、概要设计

### 3.1 方案总述

`/investigate` → `POST /api/transaction-checks` → 新局部 Reader → 新解释 Service → 严格 Zod 报告。配置只从服务器 ETHEREUM_RPC_URL 读取。

### 3.2 模块边界

Reader 位于 `modules/transaction-check/`，只依赖 viem、局部合同及现有只读常量；Service 从 Reader 结果形成结论。Integration 和 API 不调用 Guardian runtime。前端只接局部报告。

### 3.6 专项设计检查

| Lens | 结果 |
| --- | --- |
| api-designer | 独立 POST 查询，runtime 校验，Problem JSON，明确状态语义，记录 OpenAPI；不分页，不新增认证系统 |
| architecture-designer | 不复用执行器作读取，不依赖 Portfolio，不接持久化；只读局部适配能力，兼容现有模块 |

## 四、详细设计

### 4.1 局部合同

#### 4.1.1 需求内容

**D-001 / Data Contract / AC-001/002/003/005：** 请求 `{ txHash }`。新增 `TransactionCheckReport`：mode/network/checkedAt、observation（transaction/supportedSwaps/evidence/scope）、classification、headline/summary、confirmedFacts/uncertainties/nextSteps。transaction 包含 hash/from/to（合约创建可为 null）、nativeValueEth/input/status/blockNumber/blockHash/timestamp/logCount。supportedSwaps 包含 logIndex、direction、wethAmount、usdcAmount、poolAddress。精确金额为十进制字符串；引用复用 OnchainEvidence。

#### 4.1.2 方案设计

classification 为 `SUPPORTED_POOL_SELL`、`SUPPORTED_POOL_BUY`、`SUPPORTED_POOL_MIXED`、`NO_SUPPORTED_SWAP`、`REVERTED`。据实际方向集合决定，不能由前端指定。失败回执不得带成功 Swap。NO_SUPPORTED_SWAP 的含义是“本次范围没有足以支持兑换分类的证据”。

#### 4.1.3 流程步骤

输入校验 → 读取事实 → 元数据与日志校验 → 确定分类 → 中文报告 → schema 校验。

#### 4.1.4 边界条件

哈希格式错误拒绝；金额不转为浮点数；双向事件不合并成净方向。零量 Swap 不作为非零方向证据。局部报告内部分类、状态、金额和事件引用必须一致；CONTRACT_EVENT 引用数量必须等于支持的 Swap 数量，且所有事件引用合约必须匹配观察范围内的池。

#### 4.1.5 不变行为

现有 OnchainSignalState、RiskAnalysis、PolicyDecision、ExecutionResult 的字段、权限与含义保持。新增报告不构成其中任一合同。

### 4.2 只读事实与解释

#### 4.2.1 需求内容

**D-002 / Behavior Contract / AC-002/003/004：** 只核验固定池，USDC 是代币数量，不按 $1 伪造美元估值。

#### 4.2.2 方案设计

读取 chainId=1、tx、receipt、tx 所在 block。核对 hash、blockNumber/blockHash、from/to、状态与日志引用；检查区块时间。按交易历史 blockHash 读取 token0/token1/fee/decimals，确认 USDC/WETH 与 500。固定池 Swap 采用严格解码及编码回检；金额方向与精度验证。最后重读 blockNumber 核对 canonical hash，发现变化整体失败。

**D-003 / Behavior Contract / AC-004/005：** 结论仅覆盖外层事实及本池内事件；始终声明未获取 trace/后续转账/CEX、身份未核验。检测到卖出事件不等于该主体在全笔交易净卖出，不能推断市场原因。

#### 4.2.3 流程步骤

事实核验 → 支持池元数据 → 逐日志判断 → canonical 校验 → 确认事实及不确定性说明。

#### 4.2.4 边界条件

**D-004 / Operational Contract / AC-006：** 未找到为 404，pending 为 409；reverted 为正常报告但没有兑换结论。错链、RPC/元数据/回执/日志/重组异常为 503，detail 使用固定安全文案。未知异常不回传 cause 或 RPC URL。无自动重试、旧数据或 Mock 回退。重复与并发为独立只读，无事件预占；没有存储迁移。

#### 4.2.5 不变行为

既有 Reader、卖压统计和 Guardian 不调整。新查询不读或写保护钱包数据库。

### 4.3 页面与 HTTP

#### 4.3.1 需求内容

**D-005 / Interface Contract / AC-001/006/007：** `/investigate` 中文表单，只填 hash；`POST /api/transaction-checks` 只接请求合同，返回200报告。沿用本机同源校验，但将错误转为本查询 Problem。可手动填入已核验的大额转账示例，示例按钮仍发真实 RPC，不使用保存的 JSON 当在线结果。

#### 4.3.2 方案设计

页面展示头部只读范围、结论、外层事实、兑换事件、不能确认项、出处和下一步。RPC 只在服务端。成功及错误响应均 no-store；错误为 application/problem+json，type 为 `urn:xjy:transaction-check:<code>`。

#### 4.3.3 流程步骤

填入 hash → 查询/loading → validate response → 展示或具体错误；请求期间禁止重复提交，新的查询清除旧报告。

#### 4.3.4 边界条件

空输入禁提交；格式错误本地提示且服务端拒绝；旧请求结果不能覆盖新输入；引用链接只指向已校验的 Etherscan 交易/区块/合约。配置缺失明确提示，不能展示在线成功。权限失败403/媒体类型415沿用旧访问边界。

#### 4.3.5 不变行为

首页保护按钮与旧 API 保持；仅增加核验导航。Guardian 启停和数据库不为本验收重置。

## 七、接口设计

POST 查询的请求及响应由局部 Zod 合同固定，OpenAPI 从 Zod 导出并记录错误 enum；新资源尚无旧客户端，版本为1.0.0。只产生一个报告，不分页；本机同源、固定单池、有限 RPC 调用，不增加公开服务限流系统。

| 状态 | 意义 |
| --- | --- |
| 200 | 已确认上链交易的核验报告，包括 reverted |
| 400 | JSON/哈希非法 |
| 403 / 415 | 本机同源或媒体类型限制 |
| 404 | 交易未找到 |
| 409 | 交易尚未确认 |
| 503 | 配置、RPC、错链或事实校验失败 |

### 10.5 Planning Handoff

**D-006 / Workflow Contract / AC-008：** 根代理固定局部合同并顺序整合；Reader/Service 和页面分别在不同目录实现；根代理负责 HTTP、测试、文档与真实验收。允许决定局部函数和 CSS 命名；扩大协议/资产/权限或改旧合同需重新澄清。
