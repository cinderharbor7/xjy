# 从真实案例寻找产品价值

研究日期：2026-10-07（北京时间）。这是产品研究与待验证建议，未改变已冻结的合同、分工或工程路线。本次不修改核心代码。

## 现在能得出的判断

**最值得先检验的任务是：收到一条 ETH 异动消息后，把其中的说法核验成一份可以复查的简报。** 例如：这笔钱只是转账，还是已有实际卖出的证据？金额、方向、时间是否正确？身份来自谁的标签？哪些结论还缺资料？

真实案例提供了“事故中有人需要理解情况”的直接线索，也暴露了把链上记录解读成交易建议的风险。它们尚未证明你们的产品有用户、比现有工具更好，或有人愿意付费。自动减仓的需求和授权意愿也没有得到验证。

当前最薄弱的环节是：我们还不知道谁会反复完成这项核验、报告交给谁，以及旧办法到底在哪一步耽误了工作。不能用一个听起来合理的用户画像补上这些空白。

## 案例一：Maker 黑色星期四，社区明确需要情况说明

2020 年 3 月 12 日，Maker 社区的紧急响应讨论中，发帖者 LongForWisdom 征求一份情况说明，让参与者理解发生了什么，再讨论处理方案。[原始社区讨论](https://forum.skyeco.com/t/black-thursday-response-thread/1433)

这里有一个真实表达出来的任务：把正在发生的复杂事件整理成共同理解的材料，支持多人讨论下一步。相比泛泛的“大家想少亏钱”，这是更具体的需求线索。

需要保留两个边界：参与者处于协议治理和紧急响应情境，不能据此认定普通 ETH 持有人都有相同需求；页面中的首帖包含后来汇总的情况说明和讨论，不应把全部内容当作发帖瞬间已知的信息。本次未核验该帖完整编辑历史。

**对产品的启发（推断）：** 简报的价值可能在于帮助团队形成可讨论、可追溯的共同事实。你们仍需证明，自己的流程能比现有工具加人工整理更好地完成这项工作。

## 案例二：真实的 20,059.2 ETH 转账，能证明到哪一步？

选取以下 Ethereum 主网交易，并在本次研究中通过 JSON-RPC 独立查询交易、成功回执和对应区块，核对 chain ID 与区块哈希。查询没有签名或广播交易。公开核验结果摘要保存在 [核验记录](research/eth-transfer-2024-08-03.json)。

| 核验项 | 链上读取结果 |

| 交易时间 | 2024-08-03 18:08:23 UTC |
| 金额 | 20,059.2 ETH |
| 区块 | 20,449,709 |
| 发起地址 | `0x98629555d323324b9415471033f2745c57b608c6` |
| 接收地址 | `0xf584f8728b874a6a5c7a8d4d387c9aae9172d621` |
| 交易状态 | 成功 |
| 外层 input / 回执日志数 | `0x` / 0 |

交易哈希：[`0x19b45706e3877b8cb19133dbdc6f8013a5a4a033495e7b070c84977620348e8a`](https://etherscan.io/tx/0x19b45706e3877b8cb19133dbdc6f8013a5a4a033495e7b070c84977620348e8a)。本次链上事实来自 RPC 核验；浏览器链接用于读者复查，不代表本次成功抓取了该浏览器页面。

[Whale Alert 的记录](https://whale-alert.io/transaction/ethereum/0x19b45706e3877b8cb19133dbdc6f8013a5a4a033495e7b070c84977620348e8a)将接收地址标为 Jump Trading。这个名称是外部服务的标签，链上交易本身不独立证明地址归属。

可以用它设计一个演示问题：**“这笔约 2 万 ETH 的交易，是否已经证明大户卖出并导致 ETH 下跌？”** 这是本研究拟定的测试说法，未找到有人针对这笔交易发布该原话的证据。

一份合格的简报应回答：

> **已确认：** 该地址向另一地址转出 20,059.2 ETH，交易成功，时间和区块已核对。
>
> **证据范围：** 已读取外层交易和回执，没有获取内部调用 trace、后续资金路径或交易所成交记录。
>
> **尚不能确认：** 这笔记录不足以证明实际出售、出售动机或价格下跌的原因；现有核验也不足以排除其他交易中发生卖出的可能。
>
> **后续调查需要：** 核验地址标签出处，查看限定时间范围内的后续路径及可能的兑换记录；即使找到卖出，也仍需更多分析才能讨论对市场价格的影响。

**对产品的启发（假设）：** 帮读者发现说法超出了证据范围，可能比增加一个风险分数更有用。但只查这一笔交易，浏览器加几句人工说明可能已经足够；这还没有证明需要一个新产品。

## 案例三：2024 年 8 月 5 日，清算损失与协议坏账要分开看

Chaos Labs 在 Aave 社区发布的报告称，截至 2024 年 8 月 5 日 19:00 UTC，所覆盖部署的清算抵押品约为 2.7671 亿美元，其中 Ethereum 超过 2.33 亿美元；报告未识别到新增坏账。[8 月 6 日风险报告](https://governance.aave.com/t/chaos-labs-risk-report-insights-from-recent-market-events-06-08-24/18554)

这是风险服务商的汇总，本研究没有逐笔重算其清算总额。报告能支持“发生大量清算”和“报告未发现协议坏账”同时成立，不能说明每个用户都安全。

同一轮波动中，Chaos Labs 对 ether.fi 的报告称，当时主要服务和提款仍在运行，并说明 weETH 抵押、借入 ETH 的相关资产仓位与一般美元计价负债仓位有所不同。[8 月 5 日报告](https://governance.ether.fi/t/chaos-labs-recent-market-volatility-post-mortum/2054)

**对产品的启发（推断）：** “ETH 下跌”“用户被清算”“协议出现偿付问题”需要各自的证据。简报要写清讨论对象与适用范围。不同仓位受到的影响不能由一个市场分数统一推出。

这些报告包含事后信息。历史回放若使用它们，必须注明发布时点，不能宣称 Agent 在事前已知道报告结论。当前钱包 ETH/USDC 读取也不等于已经识别所有 DeFi 杠杆仓位。

## 反例：换成 USDC 不能直接证明保护成功

2023 年 3 月的 USDC 脱锚事件中，Circle 公告披露了存于 Silicon Valley Bank 的 33 亿美元储备，并说明监管措施后的可用性。页面标注发布日期为 3 月 13 日，正文新闻日期为 3 月 12 日。[Circle 公告](https://www.circle.com/pressroom/3-3-billion-of-usdc-reserve-risk-removed-dollar-de-peg-closes)

**对产品的启发（推断）：** 降低 ETH 敞口与降低最终损失是两项不同的结果；防御资产也有自己的风险。因此，现有 Fork 演示能证明受限执行和余额变化，不足以证明策略总能保护用户。本研究不据此新增资产、保险或其他执行功能。

## 现有工具已经能做什么

下表来自厂商官方文档，仅说明其公开提供的能力。本次没有登录这些产品做任务耗时对比，也没有独立验证厂商效果宣传。

| 现有工具 | 已有能力 | 对本项目的要求 |
| --- | --- | --- |
| [Arkham 资金调查工具](https://info.arkm.com/research/crypto-transaction-monitoring-explained) | 地址标签、交易筛选、资金路径追踪、告警 | 不能把资金追踪或告警本身当成新差异 |
| [Arkham Risk Scores](https://info.arkm.com/announcements/risk-scores) | 非法活动关联评分，以及解释理由和关联地址的简报 | “有评分、有解释”已有人提供；其评分也不等同于 ETH 下跌风险 |
| [Phalcon Explorer](https://docs.blocksec.com/phalcon/phalcon-explorer/quick-start) | 按交易哈希查看资金流、余额变化和调用关系 | 只把交易信息改写成自然语言，可能没有足够增量 |
| [Forta Attack Detector](https://docs.forta.network/en/latest/attack-detector-bot/) | 组合多条告警，按攻击阶段组织线索 | 多信号协作也已有实现，不能只靠“Agent 协作”命名形成价值 |
| [Phalcon Security](https://docs.blocksec.com/phalcon/phalcon-security) | 官方描述包括监控与自动防护动作 | 自动保护概念本身不能证明差异；其安全场景与本项目市场卖压也不应混同 |

可以检验的增量是：同样面对一条待核验消息，是否更快形成可靠简报，减少遗漏和无依据的结论。这个增量目前未测量。

## 一个足够小的产品假设

**候选使用者：** 小型 Web3 团队里，收到 ETH 异动消息后需要核验并给其他人出简报的人。这个角色及其使用频率尚未通过访谈确认；Maker 案例不直接验证这个目标群体。

**任务：** 当一条带地址或交易哈希的 ETH 异动消息需要被核验时，我想分清已发生的事实、还不能支持的解释和缺失资料，以便交出一份别人可以复查的简报。

第一轮只检验“大额 ETH 转账是否已有卖出证据”这一类问题。一个输入、一份短报告；不要把需求扩成解释全部链上异常或预测 ETH 走势。

报告必须交代四件事：确认发生了什么、不能确认什么、每条判断依据什么、下一步还缺什么资料。事实注明链、时间、区块和来源；标签注明提供者；无法调查的范围明确保留。不能用高 Confidence 替代缺失的证据。

这个任务可能产生的价值包括核验时间减少、交接时少丢证据，以及降低传播错误说法的风险。这些都是待测假设，目前没有用户行为数据支持。

使用者可能继续选择旧办法：浏览器已经足够快；可靠身份标签或路径数据更重要；新报告增加了检查负担；市场消息偶尔看看即可。也可能不愿采用：担心 Agent 用流畅文字包装猜测，或不清楚数据是否完整。需要逐项检验这些阻力。

## 没有真实用户时，先验证哪一件事

先做一次手工对比，不开发新页面：

1. 选三笔真实交易：本文已核验的转账、一笔有明确兑换证据的 DEX 卖出、一笔调查范围内证据不足的交易。后两笔尚未选定，不能算作已完成样本。
2. 为每笔设定相同截止时点、允许使用的工具和资料范围。避免一组得到更多数据，或用事后报告回答事前问题。
3. 两名队员分别用原有工具整理简报、按拟议流程整理简报。记录来源、制作耗时及检查耗时。交叉换人、换案例，减少个人熟练度影响。
4. 由不知道制作方式的第三人复核；导师若愿意，可以检查专业判断。先核对正确性，再比较时间。

| 检验项 | 如何判断 |
| --- | --- |
| 可复核 | 每条事实有对应来源，读者能独立找到 |
| 有边界 | 不把转账写成已证实卖出，不把标签当作链上身份证明，不虚构价格因果 |
| 有增量 | 相比原始交易页，实际解决了一个预先写明的问题 |
| 少负担 | 制作加复核的总耗时有改善，不能只统计生成文字的速度 |
| 能交接 | 读者能复述确认结果和缺失证据，知道下一步查什么 |

**停止条件：** 如果得到的只是更漂亮的摘要，现有工具几步就能完成，或者检查报告耗时抵消了制作节省，就暂停扩展这个方案。三笔样本通过也只说明能力和可能的效率增量，不能宣称市场需求成立。

真正尚待确认的是：谁反复承担这项任务、频率与代价如何，以及什么改善值得他换工具。导师若没有亲自做过这项工作，其评价只能用于专业性和可读性检查，不能作为用户采用证据。

## 对当前项目和比赛演示的建议

保留现有代码与权限边界，暂缓增加自动减仓、风险梯度和更多资产。优先把一份真实案例简报做完整，并检验它相对现有办法的增量。上述是产品建议，不是已批准的新路线或实现任务。

如果团队决定采用这一假设，比赛展示可从一条待核验说法开始，展示原始交易、核验过程、结论和无法确认的部分。Agent 的作用需要体现为调查任务的推进与核验质量；有多个 Agent 或一段流畅解释不构成完成度证据。

按照团队提供的赛题要求，这样的展示可以回应 Ethereum 数据利用、分析可信度、工具协作及应用价值。但用户需求尚未验证应如实说明，不能把历史损失金额包装成可避免的损失。现有 Mock/Fork 换仓可作为受限执行能力的独立演示，其成功不替代产品价值验证。

可暂用的一句话：**我们正在验证一个 Ethereum 异动核验助手：把一条带链上线索的消息，整理成能复查、明确结论边界的简报。**
